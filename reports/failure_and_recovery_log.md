# Failure and recovery log

- Package preparation completed successfully. A trailing shell-only `grep` for an unavailable `/proc/vmstat` field returned nonzero after preparation had passed; the empty evidence file and kernel journal evidence were preserved.
- The first TensorRT parser launcher failed before parsing because the clean Python environment filtered the TensorRT user-site path. Its traceback was preserved as `logs/tensorrt_parser_import_failure.log`. The package-local scripts were corrected to insert only the known TensorRT Python directory at runtime, and the actual parser gate was then executed once.
- The first engine-builder launcher terminated with SIGILL (exit 132) while importing its module, before entering `main()` or invoking any TensorRT builder API. An import-only probe reproduced the issue and identified the Jetson-specific NumPy/TensorRT initialization order. The empty engine directory and original one-line console log were preserved; the package-local builder was changed to initialize NumPy before TensorRT, then verified with an import-only probe before the first actual build call.
- The first actual builder call completed and serialized the fresh strict-FP32 engine, then the same process failed during post-build metadata validation because TensorRT 8.0.1 `trt.nptype()` references the removed NumPy 1.24 alias `np.bool`. The engine was not rebuilt. The package runtime replaced only that deprecated dtype helper with an explicit TensorRT-to-NumPy mapping, and a separate clean no-inference process completed deserialization, binding, shape, and dtype validation.
- The 20-image correctness gate completed with 20/20 console passes and saved all backend predictions, then failed while serializing a NumPy boolean into its JSON summary. Those 20 executions were not repeated. The summary was reconstructed offline from the saved prediction CSV and original 20 pass lines; raw-difference values that were not serialized are explicitly marked unavailable rather than guessed. The shared JSON writer was made NumPy-scalar compatible for subsequent phases.
- A pre-acceptance second-pass audit found that preprocessing stage durations from `perf_counter_ns()` had been multiplied by 1000 while labeled milliseconds. Engine, transfer, postprocessing, end-to-end, wall-clock, telemetry, energy, predictions, and metrics were unaffected. Original timing CSVs were preserved under `raw/pre_timing_unit_correction/`; preprocessing fields in warm-up and official CSVs were corrected offline by the exact factor 1e-9, dependent analyses/figures/reports were regenerated, and the final validator gained a per-row unit/decomposition gate. No inference was rerun.
- A third-pass report audit found that the bottleneck selector compared atomic stages with aggregate totals and therefore selected transfer-inclusive inference. The selector was corrected offline to compare independently timed atomic stages only; the TensorRT engine is the resulting atomic bottleneck. No measured value changed and no inference was rerun.
- The ONNX export SSH control channel timed out after launch, but the single remote exporter continued and completed successfully; no duplicate export was started.
- No official benchmark execution was retried, discarded, or hidden. ONNX and ONNXRuntime were supplied by the existing `jetson_benchmark_env` through a recorded PYTHONPATH; no package was installed or upgraded. PyCUDA remained unavailable and was intentionally not used; CUDA Runtime ctypes provided allocation, copies, streams, events, and synchronization.
